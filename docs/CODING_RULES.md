# 코딩 규칙

## 일반

- TypeScript를 사용한다.
- 단순한 해결 방법을 우선한다.
- 필요 이상의 추상화를 사용하지 않는다.
- YAGNI(You Aren't Gonna Need It)를 기본 원칙으로 한다.
- 성능 최적화를 미리 수행하지 않는다.
- 명확한 필요성이 없는 라이브러리를 추가하지 않는다.
- 기존 코드를 존중하고 필요한 부분만 수정한다.
- 기존 코드로 해결할 수 있는 문제에 새로운 구조를 추가하지 않는다.
- 작은 프로젝트라는 사실을 항상 고려한다.

## Angular

- Standalone Components를 사용한다.
- Angular의 현재 권장 패턴을 우선한다.
- 로컬 상태에는 Angular Signals를 우선적으로 사용한다.
- Template에서만 사용되는 멤버는 가능한 경우 `protected`를 사용한다.
- Template은 읽기 쉽게 유지한다.
- Angular의 Control Flow인 `@if`, `@for` 등을 우선적으로 사용한다.
- 새로운 코드에서는 `*ngIf`, `*ngFor` 등의 구문을 사용하지 않는다.
- Component에는 UI와 직접 관련된 로직을 중심으로 작성한다.
- Component가 지나치게 복잡해지지 않도록 한다.

## 상태 관리

로컬 상태에는 Angular Signals를 우선적으로 사용한다.

기본적으로 다음과 같은 방식으로 상태를 변경한다.

```typescript
signal.set(...)
signal.update(...)
```

수동으로 mutable 상태를 관리하기보다는
Signal을 통해 상태 변경을 명확하게 표현한다.

파생 상태가 필요한 경우 `computed()`를 우선적으로 검토한다.

`effect()`는 꼭 필요한 경우에만 사용한다.

## 함수

- 함수는 작고 명확하게 유지한다.
- 하나의 함수에는 하나의 명확한 책임을 부여한다.
- 동일한 로직을 여러 곳에 복사하지 않는다.
- 단, 몇 줄 정도의 단순한 코드까지 무리하게 공통화하지 않는다.
- 함수 이름만 보고도 역할을 이해할 수 있도록 한다.

## 네이밍

변수, 함수, Component 등의 이름은
역할을 명확하게 알 수 있는 구체적인 이름을 사용한다.

다음과 같이 의미가 불분명한 이름은 가능한 한 피한다.

```text
data
temp
value
foo
test
```

단, 일반적인 문맥에서 의미가 명확한 경우는 예외로 한다.

## 의존성

새로운 npm 패키지를 추가할 때는 다음 조건을 확인한다.

1. 왜 필요한지 명확해야 한다.
2. Angular 또는 브라우저의 기존 API로 대체할 수 없어야 한다.
3. 프로젝트의 복잡성을 불필요하게 증가시키지 않아야 한다.

기존 API만으로 충분히 구현할 수 있다면
새로운 Dependency를 추가하지 않는다.

## 랜덤 선택

단순히 배열에서 하나의 항목을 랜덤으로 선택하는 경우
`Math.random()`을 사용한다.

예를 들어 다음과 같은 단순한 선택에는
배열 전체를 Shuffle하지 않는다.

```typescript
const selected = options[Math.floor(Math.random() * options.length)];
```

여러 항목을 섞어야 하거나
중복 없이 여러 번 선택해야 하는 경우에만
Fisher-Yates / Durstenfeld Shuffle을 검토한다.

## 에러 처리

사용자가 이해할 수 있는 상태와 메시지를 우선한다.

기술적인 에러 메시지를 그대로 사용자에게 표시하지 않는다.

사용자에게 필요한 정보만 간결하고 이해하기 쉬운 일본어로 표시한다.

## 주석

코드만으로 의도를 이해하기 어려운 경우 주석을 추가한다.

코드 자체로 충분히 이해할 수 있는 내용을 설명하는
불필요한 주석은 작성하지 않는다.

주석을 작성할 경우
"무엇을 하는가"보다 "왜 그렇게 하는가"를 설명하는 것을 우선한다.

## 리팩토링

기능을 추가하거나 수정할 때
관련 없는 코드를 함께 리팩토링하지 않는다.

변경 범위는 필요한 최소한으로 유지한다.

기존 기능과 UI를 의도하지 않게 변경하지 않는다.

## 코드 생성 시 원칙

새로운 코드를 작성하기 전에
현재 프로젝트의 구조와 기존 구현을 확인한다.

이미 존재하는 Component, Service, Utility 또는 스타일을
재사용할 수 있는지 먼저 확인한다.

새로운 파일이나 구조를 생성할 때는
현재 요구사항에 실제로 필요한지 판단한다.

미래에 필요할지도 모른다는 이유만으로
미리 코드를 작성하지 않는다.
